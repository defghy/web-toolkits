# 互联网技术知识地图：技术实现方案

状态：待审阅；已建立普通 Web 项目骨架，知识地图尚未开发。  
日期：2026-11-04。  
项目：`packages/wtool-know-map`。

## 1. 本轮目标

页面只有一张可交互的知识地图，采用类似 webpack 包分析的嵌套矩形效果：大矩形表示职责或领域，点击后在矩形内部显示子分类，再继续展开到库、框架、产品与工具。

以**互联网产品的职责层级**组织主地图，从用户界面逐层深入到服务、数据和运行基础。前端 → 后端 → 数据 → 系统只是概览，不固定为四层；职责数量、职责内部阶段与分类深度均由数据配置，允许分支和跨层关系。职责按产品视角的上下游顺序纵向排列，每层内部采用**矩形树图（Treemap）**呈现分类包含关系。浏览同时包含“向下了解支撑职责”和“在矩形内展开技术分类”。

页面进入后只有**一个搜索框和一张层级图**，搜索框之外的绝大多数可用面积用于图。首版支持逐级展开/收起、局部聚焦、路径搜索与节点内的简短技术说明；不设置页面标题栏、工具栏、面包屑、常驻说明栏、图例或额外按钮。职责上下游体现在图内的顺序中，具体调用、数据来源和运行依赖保留为带场景的关系数据。首版不增加独立关系图或链路视图。

知识数据以主要功能范围完整为目标，先录入代表实现，后续持续补充，不以穷举全部互联网技术为验收要求。

## 3. 图形方案与技术选型

### 3.1 为什么选 Treemap

主地图采用由数据配置顺序与数量的职责分层布局，Treemap 用于各层内部的“领域 → 子领域 → 技术”分类，保留矩形内部逐渐出现更多矩形的交互。Treemap 本身不表达调用先后，不能依靠 squarify 的矩形位置推断上下游。

它能提高空间利用率，但屏幕仍有可读性限制。首版通过“按需展开 + 放大聚焦 + 层级返回”浏览大量知识，不把几千个标签同时压进一个视口。

| 方案                   | 适配情况                                                | 结论                                               |
| ---------------------- | ------------------------------------------------------- | -------------------------------------------------- |
| G6 Rect Combo          | 支持节点与子 Combo 嵌套、折叠，适合同时展示分组与关系边 | 可用于未来关系探索，但矩形区域的铺满布局需额外处理 |
| G2 Treemap             | 提供矩形树图与下钻交互                                  | 合适备选；若采用标准点击下钻，可直接使用           |
| D3 hierarchy + Vue SVG | 职责按配置排序，D3 计算层内矩形，Vue 控制展开与说明     | 首版采用，方便精确控制“在原矩形内展开”的行为       |
| 力导向、普通树图       | 更侧重关系或层级连线，需要较多空间                      | 当前交互不采用                                     |

上述能力参考 [G6 Combo 文档](https://g6.antv.antgroup.com/en/manual/element/combo/overview/)、[G2 Treemap 文档](https://g2.antv.vision/zh/charts/treemap/) 和 [D3 Treemap 文档](https://d3js.org/d3-hierarchy/treemap)。技术选型基于本项目的局部展开交互，不要求使用 G6。

### 3.2 技术栈

- Vue 3 + TypeScript + Vite，沿用现有项目骨架。
- 自有布局逻辑负责主职责层和层内有序阶段；`d3-hierarchy` 只负责分类区域的 Treemap 布局，配套类型声明，不引入整个 D3。
- Vue SVG 负责矩形、文字、层级边框、节点内说明与交互；Vue DOM 负责唯一的搜索框和输入时的临时候选列表。
- Composition API 管理状态，CSS 变量管理配色；首版不引入完整 UI 框架与状态管理库。
- vue-tsc、数据校验脚本和 Vitest 验证类型、数据不变量、路径与布局规则。

后续安装时选择与现有工作区兼容的版本并更新锁文件，优先对齐仓库的 Node 22 环境。首版只有一个图引擎实现，不同时引入 G6、G2 与 D3。

## 4. 产品职责层级与分类入口

### 4.1 层数不固定，从用户界面逐步深入

主地图采用互联网产品视角：越靠上越接近用户操作，越靠下越接近数据来源与运行基础。“上下级”表示职责支撑关系，不表示组织汇报关系，也不表示下一层是上一层的子分类。

“前端 → 后端 → 数据 → 系统”只概括大的范围，不能作为固定四层的实现限制。以手机 App 为例，可进一步细化为以下职责：

| 浏览顺序示例 | 细化职责           | 典型内容                              | 展示分组示例       |
| ------------ | ------------------ | ------------------------------------- | ------------------ |
| 1            | 用户界面           | 页面、组件、布局、交互                | 用户界面与客户端应用 |
| 2            | 客户端应用与架构   | 路由、状态管理、表单、国际化          | 用户界面与客户端应用 |
| 3            | 接入与流量         | CDN、反向代理、负载均衡、API 网关     | 接入与流量         |
| 4            | 服务与业务         | BFF、业务接口、业务规则               | 后端与服务         |
| 5            | 服务协作           | 服务调用、消息队列、异步任务          | 后端与服务         |
| 6            | 数据访问           | 查询封装、ORM、连接池                 | 后端与服务         |
| 7            | 缓存               | 读取加速、热点数据                    | 数据与存储         |
| 8            | 持久化与存储       | 数据库、文件、对象存储                | 数据与存储         |
| 9            | 语言与运行时       | 编程语言、JavaScript 引擎、Node.js、JVM | 语言与运行时       |
| 10           | 部署与资源管理     | 容器、容器编排、资源调度              | 部署与资源管理     |
| 11           | 操作系统与虚拟化   | 进程、内存、文件系统、虚拟机          | 操作系统与虚拟化   |
| 12           | 基础设施           | CPU、内存、磁盘、网络                 | 基础设施           |

表中顺序用于浏览职责深度，不是十二个必经调用步骤，也不是固定十二层的行业标准。分组只是便于嵌套分类，可随知识数据增加、拆分或调整；图组件不硬编码四层、十二层或这些分组名称。初版使用表中的细化职责建立内容骨架，具体技术再按需展开。

客户端通信与存储在“用户界面与客户端应用”下独立成层，包含请求与数据获取、实时通信、浏览器存储、本地数据库、缓存、离线与 PWA。它不隶属于某个 UI 框架，也不等同于后端的接入与数据层。

实际关系需要允许分支、跨层与共享依赖：

- 接口可直接读取数据库，也可先读缓存；服务协作中的消息队列是可选支线，不必位于每个请求的数据访问路径上。
- 服务网格归在“后端与服务 → 服务协作 → 微服务 → 服务治理”下，作为可选方案；微服务架构不要求采用服务网格，服务网格也不是接入请求的必经层级。
- 搜索、对象存储等是独立数据能力，不必串在缓存与数据库之间。
- 客户端、后端、缓存和数据库各有自己的运行基础；语言运行环境不是数据库之后才会执行的步骤。
- 原生编译程序可以直接运行于操作系统，应用也可以不使用容器或编排；虚拟化不是所有部署的必经层。

工程与交付、可观测性和安全等放在同一图中的“跨层支撑”分类区域，不编造它们在主请求链中的位置。接入与流量已有主入口；DNS、网络、消息等技术可以按职责在其他入口共享引用。

职责顺序、分类包含和具体技术关系分别建模：

- **职责顺序**：按数据配置从面向用户的职责向运行基础排列，支持任意数量的职责及局部阶段。
- **分类包含**：前端包含 Web 端，Web 端包含 UI 框架；用嵌套矩形表示。
- **技术关系**：调用、读取、数据来源、运行和管理分别记录关系类型与场景，不把依赖方和被依赖方直接设为分类父子。

### 4.2 数据内部的上下游顺序

在“数据库作为数据源、缓存加速读取”的场景下，数据层默认按以下顺序展示：

```text
数据与存储
├─ 读取加速阶段：缓存
│        ↓ 缓存未命中时向下读取；读取结果用于回填缓存
├─ 持久数据阶段：数据库
└─ 其他数据能力：搜索、对象存储、数据分析等
```

缓存排在数据库上方，表示更接近读取方；数据库提供该场景的持久数据来源。缓存与数据库仍然是“数据与存储”下的两个分类，数据库不嵌套在缓存内部。缓存命中时不必访问数据库；写入与失效策略在具体关系说明中表达，不从上下位置推断。

这个顺序适用于上述场景，不将所有缓存都定义成来自数据库。例如浏览器缓存的来源可能是接口响应或静态资源，应在对应的前端或通信入口中说明。Redis 在缓存与数据库入口共享实体，但只有承担缓存职责的入口处于读取加速阶段。

搜索、对象存储、数据分析不强制串到“缓存 → 数据库”之后，使用独立分类区域；有明确数据来源时再记录对应关系。上下游顺序在全景与聚焦后保持一致，普通分类不设置虚假的先后关系。

客户端应用与架构归入用户界面层：App、桌面窗口和小程序都只是界面的承载形态，路由、状态、表单与国际化服务于这些界面。通信、存储和离线能力被所有客户端应用共享，也会与后端、数据层发生关系，因此作为“客户端通信与存储”独立成层，而不是某个 UI 框架的子类。

这是内容录入结构示例，后续逐项核验具体库的能力和来源。例如 PixiJS 不只使用 Canvas，分类中的说明要标注渲染后端，不能用展示入口代替完整技术定义。

平台与专业能力是不同维度。GIS、3D、Canvas 不只属于某一个终端；CesiumJS 可同时关联 GIS 与 3D。允许多个展示入口引用同一个技术实体，不强制所有技术只出现一次。工具与语言、协议、框架分别标注类型。

### 4.5 容器的位置与内部职责

容器归入**部署与资源管理**，在容器化部署场景中位于应用运行环境和操作系统之间。以下以 Linux 容器中的 Node.js 服务说明运行依赖：

```text
业务服务
  ↓ 运行于
Node.js 语言运行环境
  ↓ 应用与运行环境被打包进镜像，并在容器中运行
容器化运行环境
  ↓ 通过容器运行时使用宿主内核能力
Linux 操作系统内核
  ↓ 使用
基础硬件资源
```

这里描述运行依赖；Node.js 进程本身运行在容器中，容器使用宿主内核，不为每个容器提供独立的完整操作系统内核。[Docker 官方概述](https://docs.docker.com/get-started/docker-overview/)

部署领域的分类进一步拆分为：

```text
部署与资源管理
├─ 镜像构建与分发：镜像构建、镜像仓库
├─ 容器运行：创建、启动、隔离与资源限制
└─ 容器编排：部署、调度、扩缩容，例如 Kubernetes
```

这三个分类按职责组织，不当成业务请求必须经过的三个阶段。镜像构建与分发也可从“工程与交付”共享引用；Kubernetes 对容器化工作负载提供编排管理，应记录工作负载 → 编排系统的 `managed-by` 关系，而不是把编排系统当成应用调用操作系统的中间步骤。[Kubernetes 官方概述](https://kubernetes.io/docs/concepts/overview/)

语言运行环境与容器运行时需要明确区分：前者执行应用代码，后者负责容器运行相关能力，不能因为名称都有“运行时”而合并。应用 → Node.js、容器化环境 → 宿主系统等运行依赖使用 `runs-on`；镜像构建和管理关系另行说明，不混用为调用关系。

上图的职责名称都是图内节点标题，不是图外导航或栏目。示意图仅说明范围，实际有序阶段按从上到下布局，普通分类使用 Treemap。初次进入只显示搜索框与按配置生成的职责节点；搜索框保持紧凑，图填满其余可用区域，高度不足时允许纵向滚动。

不显示页面标题栏、工具栏、面包屑、返回按钮、重置按钮、层级切换器、常驻说明栏、图例、状态栏或独立提示条。搜索建议仅在输入时临时出现，选择或关闭后消失，不占据常驻版面。

节点名称、分类子项和必要的关系文字属于图本身；技术说明在选中节点内部展开，不另开图外面板或浮层。首屏不自动展开全部技术后代，也不在每个节点放置独立操作按钮。

### 5.2 仅通过图内节点展开、聚焦与返回

1. 点击未展开分类的标题或主体：在该矩形内部显示直接子项，父区域保留标题和边框，外部兄弟区域不变。
2. 点击已展开分类的标题：收起该分类的后代。点击子节点不冒泡到祖先，不用额外的加减号按钮。
3. 子项数量或面积无法满足可读阈值时，点击分类主体直接聚焦该分类；节点内可用简短文字说明此动作，不增加独立“聚焦”按钮。普通分类也可通过双击标题聚焦；单击与双击通过统一判定避免同时触发展开/收起。触屏可长按标题聚焦，密集区域的单击聚焦不依赖长按。
4. 聚焦时在图的外缘保留可点击的祖先矩形边框与名称。点击某个祖先的标题或边框回到该范围，恢复其展开状态；这些祖先是地图节点，不生成额外面包屑或返回控件。祖先较多时仅保留可读的最近祖先，逐级返回，始终允许返回根节点。
5. 叶子技术点击后在节点内展示简短说明、类型、资料链接与带场景的相关技术入口；空间不足时先聚焦该节点。再次点击标题收起说明，点击相关入口定位关联节点。空分类在图内标注“待补充”。
6. 搜索定位也保留祖先矩形，使用户可以仅通过图回到之前的上层范围。Escape 可关闭搜索建议或节点说明，在无临时内容时退出一级聚焦；键盘操作不需要常驻控件。

图内标题及可点击区域支持键盘聚焦和 Enter 操作，可访问名称表达“展开”“收起”“聚焦”等当前动作。桌面和触屏均可通过图内节点完成必要操作，不依赖鼠标悬停或双击才能返回。

### 5.3 面积、标签与可读性

- 面积仅用于排版，不编码包体积、流行度或重要性；此规则写入节点的可访问说明，不新增图外提示条。
- 普通分类的直接子项默认使用相等布局权重；有序职责与阶段按各自配置分配区域，不按后代技术数量改变所有祖先面积。
- 每个父区域内独立布局，展开子项只改变该父区域内部，不推动其他区域。聚焦会调整当前范围的布局，返回时恢复原状态。
- 名称空间不足时截断，选中或聚焦后在节点内显示完整名称；更小区域保留父节点，点击父节点聚焦，避免大量无文字小块。
- 同一职责分组使用同色系，不同分类深度用边框与明暗区分；层级名称、上下位置与带语义的关系文字共同表达职责，不依赖图例或仅靠颜色。
- 窄屏保持职责纵向顺序，允许页面纵向滚动，触屏点击查看节点内容；图内祖先标题保留足够点击面积。

## 6. 搜索：路径展示与地图定位

搜索在整份知识数据中进行，与当前聚焦范围无关。输入 Vue 后，候选展示：

```text
前端 → Web 端 → Vue
UI 库 / 框架 · 渐进式界面框架
```

底层完整路径可能为“互联网产品技术地图 → 用户界面与客户端应用 → 用户界面 → 平台与应用形态 → Web 端 → UI 库 / 框架 → Vue”。根节点及仅用于组织维度的通用分组可从候选主路径中省略，通过路径别名将“用户界面与客户端应用”显示为“前端”；完整路径在搜索候选的临时辅助说明中保留；定位后由图内祖先节点表达所在范围，不显示面包屑。

路径基于当前分类数据生成。核心功能和区分入口的分类不得省略，例如“数据与存储 → 数据库 → 非关系型 → 键值 → Redis”。同一实体有多个入口时分别展示候选，不因共享实体而合并不同路径。

选中搜索结果后：

1. 通过展示条目 ID 找到完整祖先路径。
2. 默认聚焦到目标所属的最近可读分类，展开必要祖先及目标，确保目标矩形有可读面积；通过图内祖先节点可返回上层范围。
3. 高亮目标矩形，在节点内部显示名称与技术说明；保留可点击的祖先矩形，不新增图外详情或路径栏。
4. 连续选择时只完成最后一次定位，不被旧动画覆盖。

候选按名称/别名精确匹配、前缀、包含匹配排序，同级按路径稳定排序；支持 `k8s`、`rn`、中文功能名称。方向键切换、Enter 确认、Escape 关闭，首版展示前 20 条并提示总数。

## 7. 数据与布局实现

### 7.1 唯一实体与展示树

```ts
interface TechEntity {
  id: string
  name: string
  aliases: string[]
  kind: string // 语言、协议、库、框架、产品、运行环境等
  summary: string
  sources: { title: string; url: string; checkedAt: string }[]
}

interface MapEntry {
  id: string
  parentId?: string // 除根外必须有父节点
  label: string
  kind: 'root' | 'domain' | 'dimension' | 'function' | 'approach' | 'technology'
  entityId?: string // technology 必填
  classificationBasis?: string
  searchLabel?: string // 路径短名称，例如“前端”
  compactInSearchPath?: boolean // 仅通用分组可省略
  order: number // 分类内的稳定顺序，不代表职责上下游
}

interface LayoutGroup {
  id: string
  parentEntryId: string // 对应展示树中的父分类
  mode: 'product-layers' | 'ordered-stages' | 'treemap'
  orderedEntryIds: string[] // 顺序布局时从上游到下游排列，数量不固定
  auxiliaryEntryIds?: string[] // 跨层支撑或不属于阶段链的其他分类
  context?: string // 阶段顺序适用的场景
}

interface TechRelation {
  id: string
  source: { kind: 'entry' | 'entity'; id: string }
  target: { kind: 'entry' | 'entity'; id: string }
  type: 'calls' | 'reads-from' | 'derived-from' | 'runs-on' | 'managed-by' | 'uses-language' | 'integrates-with'
  description: string
  context: string
}
```

一份展示树对应一张地图，技术实体可由树中多个条目引用。数据树保持唯一父节点和无环；根下的职责分组由 `product-layers` 配置数量及从上到下的顺序，支持接入、运行环境、部署、操作系统等独立分组，不硬编码为四类。分组内部可递归配置 `ordered-stages`，例如用户界面 → 客户端通信与存储、缓存 → 数据库；不存在明确先后的分类使用 `treemap` 或辅助区域。十二项职责是内容示例，不对应十二个写死的字段。

`LayoutGroup` 只控制布局，不改变分类父子关系。有序布局的顺序项与辅助项必须互斥并覆盖该组的直接子项；每个父分类至多一份布局配置，职责分组和阶段均支持继续嵌套。阶段配置必须注明场景；浏览顺序不自动生成具体调用关系，相邻项只有存在明确的关系数据时才显示带语义的关系提示。只对确有职责顺序的组使用有序布局，不把所有分类都转成链。

关系单独保存，允许跨树分支和循环，不参与 Treemap 的嵌套布局。`entry` 端点表达特定职责入口，`entity` 端点表达技术本身；职责关系如“前端调用后端”引用入口。`derived-from` 的方向是派生数据 → 来源，例如缓存入口 → 数据库入口；`reads-from` 是读取方 → 被读取方，均需说明场景。这些方向不代表缓存服务自身一定直接调用数据库，未命中查询可以由后端完成。

同一实体的不同入口具有独立的展开与选择 ID，介绍和资料共享。Redis 可以同时位于数据库与缓存，CesiumJS 可以同时关联 GIS 与 3D。

预建索引：`entryById`、`childrenByParentId`、`entityById`、`entryIdsByEntityId`、`ancestorIdsByEntryId`、完整路径与搜索路径。增补分类无需改变图组件或固定层级字段。

### 7.2 布局流程

1. 根据 `focusEntryId` 确定当前范围，默认是全局根节点；读取对应的布局配置，无显式配置时使用 `treemap`。
2. 全景根使用 `product-layers`：按配置中的职责数量和顺序分配横向带状区域，预留图内节点标题与跨层支撑区域；不硬编码四层或十二层，展开不改变外部顺序与边界。
3. 任意分类可递归使用 `ordered-stages`；例如数据层在主区域中从上到下排列缓存、数据库，旁边保留其他数据能力区域；窄屏将辅助区域排在阶段组之后，保留分组标题，避免误读为下一阶段。聚焦数据层后仍保留该顺序。
4. 普通分类将直接子项构成一层临时 D3 hierarchy，权重均为 1，按 `order + id` 稳定排序，使用 `treemapSquarify` 计算坐标。Treemap 坐标不承担上下游语义。
5. 每个父矩形预留标题与间距，只对已展开的分类递归计算内部布局。子坐标转换为统一坐标系，Vue SVG 按 `entryId` 绘制；文字不溢出父矩形。
6. 子项不能满足可读阈值时停止更深绘制，由该分类节点本身承接点击聚焦，不新增操作按钮。初始参考阈值为子块宽 96px、高 48px，实际按标签长度和视口调整。全景高度不足时允许纵向滚动，不通过重排主层挤入一个屏幕。
7. 聚焦将目标范围放大，保留原始数据、该范围的布局模式及外缘的祖先矩形；祖先坐标由祖先路径生成，不复制成新的展示条目。点击祖先标题返回对应范围，深层祖先逐级呈现，不增加面包屑。范围外的上下游通过节点内相关入口访问。

D3 只输出普通分类的坐标，Vue 统一控制 SVG 和状态，不让 D3 与 Vue 同时修改 DOM。有序区域使用确定的顺序布局，各父区域独立计算，避免展开后因后代权重变化导致全景矩形换位。

### 7.3 状态与资源管理

状态包含 `focusEntryId`、`expandedEntryIds`、`selectedEntryId`、搜索词和候选索引、聚焦历史。节点说明与搜索建议属于临时状态，展开集合按展示条目 ID 保存；祖先矩形由当前聚焦路径推导，不增加独立导航组件。

URL hash 保存聚焦与选中条目，支持分享；localStorage 保存展开状态与数据版本。URL 指定项优先于历史，失效 ID 回退到最近有效祖先或根节点。点击图内祖先节点返回相应分类范围，Escape 可逐级退出聚焦；历史用于恢复各范围的展开和选择状态，不渲染返回按钮。职责的上下游通过节点内相关入口跳转。

ResizeObserver 在尺寸改变时重新计算当前范围。快速点击、搜索、聚焦采用递增操作序号取消旧定位与动画；卸载清理观察器与事件。支持减少动态效果偏好。

初始展示由数据配置的职责分组及图内跨层支撑入口，细化阶段和技术按需展开，常见交互控制在约 200 个可见矩形，超过阈值引导聚焦。首版不增加 Worker、远程懒加载或虚拟列表。SVG 适用于此可见规模，后续实测有压力再换 Canvas，保留数据和布局接口。
